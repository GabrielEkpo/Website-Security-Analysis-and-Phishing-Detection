# AI Model Validation Report

## 1. API response meaning: prediction label vs probability vs risk score vs findings count

The API response is not a raw 0/1 classification score. It returns a human-readable prediction plus a modeled probability and a computed risk score.

Key fields:

- `prediction`: string = `"phishing"` or `"legitimate"`
- `label`: same as `prediction`; included for compatibility
- `phishing_probability`: float in the range `0.0` to `1.0`
  - This is the model-estimated probability of the positive class (`phishing`)
  - Example: `0.009` means a 0.9% phishing probability
- `risk_score`: float in the range `0.0` to `100.0`
  - This is the final UI-facing risk score
  - It is calculated as `max(probability * 100, findings_risk_score)`
- `findings_risk_score`: float from heuristic security findings only
  - This is the summed value from findings severities (`low`, `medium`, `high`)
- `findings`: list of security findings
  - `findings.length` is the findings count, not the risk score

Important model-label mapping:

- The training pipeline converts raw labels so that the positive class used by the classifier is `1 = phishing`
- In the API, that is returned in human-readable form as `"phishing"` or `"legitimate"`
- The numeric value `1` seen in some raw model or debugging output is not the same as the UI risk score

### Example

A result like:

- `prediction: "legitimate"`
- `phishing_probability: 0.009`
- `risk_score: 1.0`
- `findings: []`

means:

- The model predicted legitimate
- The phishing probability is 0.9%
- The overall risk is 1% due to the probability-only score
- There were no additional security findings

## 2. Why YouTube, Microsoft and Nigerian government/education sites returned low risk values around 1 or 0

Live validation showed the following patterns:

- `https://www.youtube.com` → `risk_score: 1.0`, `prediction: "legitimate"`
- `https://www.microsoft.com` → `risk_score: 1.0`, `prediction: "legitimate"`
- `https://www.nigerianstat.gov.ng` → `risk_score: 1.0`, `prediction: "legitimate"`
- `https://www.nuc.edu.ng` → `risk_score: 0.0`, `prediction: "legitimate"`

This is expected behavior for legitimate URLs:

- The model probability is well below the phishing threshold (`0.5`)
- `prediction` becomes `"legitimate"`
- The final risk score is based on the probability × 100, which is small for low-probability legitimate URLs
- Since there were no high-risk findings, the score stays low

The number `1` in the browser is therefore not a label or a class code; it is a small percentage-style risk value.

## 3. Are suspicious URL predictions generated by the real trained model? Do heuristics contribute?

Yes. The suspicious predictions are generated by the real trained model and then augmented by rule-based findings.

### Evidence from the live app

Examples observed in browser validation:

- `http://google.com.security-check.example/` → `risk_score: 100`, `prediction: "phishing"`
- `http://paypal-login.example/` → `risk_score: 100`, `prediction: "phishing"`
- `http://amazon-account-verify.example/` → `risk_score: 100`, `prediction: "phishing"`
- `http://university-admission.example/` → `risk_score: 100`, `prediction: "phishing"`

The backend code does this:

- calls `self.model.predict_proba([normalize_model_url(url)])[0]`
- computes `phishing_probability` from the positive class
- sets `prediction = "phishing" if probability >= 0.5 else "legitimate"`
- computes `risk_score = max(probability * 100, rule_score)`

This means:

- the model drives the classification decision
- heuristics add findings and can increase `risk_score` when the model is already borderline or low confidence
- when the model already predicts phishing with near-100% probability, the final risk score remains very high regardless of heuristic findings

For example, `http://amazon-account-verify.example/` showed both:

- `no_https`
- `suspicious_terms`

but the model’s phishing probability was already high enough that risk reached 100.

## 5. Training and testing separation / data leakage check

The training code performs a stratified split before fitting:

```python
train_test_split(
    urls,
    labels,
    test_size=0.2,
    random_state=42,
    stratify=labels,
)
```

Additional safeguards used:

- duplicate URLs are removed before the split
- the same URL cannot appear in both train and test sets after de-duplication
- the model is fit only on the training subset
- metrics are computed only on the unseen test subset

This is consistent with a leakage-safe evaluation strategy.

## 6. Same feature extraction and preprocessing during training and prediction

Yes. The model is a single saved scikit-learn pipeline:

```python
Pipeline([
    ('features', FeatureUnion([
        ('url_characters', TfidfVectorizer(analyzer='char', ngram_range=(2, 5), min_df=1, max_features=12000)),
        ('url_properties', Pipeline([
            ('extract', FunctionTransformer(extract_feature_dicts, validate=False)),
            ('vectorize', DictVectorizer()),
        ])),
    ])),
    ('classifier', LogisticRegression(...))
])
```

This means both training and prediction use the exact same preprocessing pipeline:

- character n-grams from the URL
- structured URL properties from `extract_feature_dicts()`
- the final logistic regression classifier

The saved artifact is therefore fully consistent for offline inference and model loading.
